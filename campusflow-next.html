CampusFlow Next
Reliable by design.

How I helped build a campus helpdesk CLI with strict data validation, testable components, and safeguards against corrupted records and failed saves.

01 / The problem

Student requests need structure and accountability.

Campus support teams need a consistent way to record complaints, assign responsibility, track progress and review outstanding issues. Without a clear workflow, requests can become difficult to organize and updates can be lost.

CampusFlow Next was developed as a Python command-line helpdesk to explore these workflows. The deeper engineering requirement was to protect ticket data when inputs were invalid or storage operations failed.

02 / The solution

A local helpdesk with defined rules.

The application supports ticket creation, impact-based priority calculation, assignment, structured notes, lifecycle transitions, search, reports and local JSON persistence.

04 / My contribution

Foundation, validation, notes and persistence.

Foundation and testing

I established the Python package and test structure, created a guarded test runner that fails if no tests are discovered, and configured GitHub Actions for automated checks. PR #4 ↗

Ticket models and validation

I implemented typed ticket records, validation of required fields and allowed values, ticket creation and lookup, and impact-based priority rules. These checks reject malformed records before they enter the store. PR #6 ↗

Structured notes

I implemented validated notes with unique IDs, timestamp checks and safeguards that preserve existing notes and unrelated tickets when an operation fails. PR #8 ↗

Reliable JSON persistence

I implemented strict loading and save behavior: malformed JSON, invalid schemas and duplicate IDs are rejected. Saving validates the complete store, writes and flushes a temporary file, then replaces the destination. This protects the previous file against failures before replacement. PR #10 ↗

05 / Engineering decisions

Failure handling is part of the feature.

Design principle: A successful demo is not enough. Invalid operations must not silently corrupt existing data.

Validate before mutation

Records are checked against strict data contracts. CLI changes are staged on a copy and published to memory only after saving succeeds.

Use temporary-file replacement

Directly overwriting a JSON file risks leaving a partial file if a write fails. A sibling temporary file and os.replace provide stronger protection for pre-replacement failures, without claiming perfect power-loss recovery.

Test negative paths

The repository contains tests for invalid inputs, collisions, malformed records and simulated storage failures. The current test count and CI outcome should be confirmed from the repository rather than assumed.

06 / Teamwork

Clear ownership, shared contracts.

This was a two-engineer project organized through issues, branches, pull requests, independent reviews and CI. My teammate implemented lifecycle management, search, reports, the Engineering Understanding Check and the interactive CLI. The PR history shows individual ownership and integration.

07 / Lessons and limitations

What this project taught me.

Working on CampusFlow Next strengthened my understanding of defensive programming, data contracts, regression tests, persistence safety, separation of concerns and collaborative review.

Scope: This is a local single-operator application. It does not include authentication, a hosted web UI, concurrent-writer coordination, a database server or guaranteed recovery from hardware failures. The Engineering Understanding Check is deterministic practice guidance, not AI grading.

08 / Outcome

Engineering evidence you can inspect.

The result is a functional Python helpdesk codebase with explicit validation and storage boundaries. My strongest contribution was implementing foundational data-integrity and persistence components that other workflows depend on.
